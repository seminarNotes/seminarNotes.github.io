Project Overview

This project addressed the critical challenge of automating volatility surface calibration for stock options. The existing Excel VBA-based mixture model was replaced with a more robust SABR (Stochastic Alpha-Beta-Rho) framework, enabling full automation and reducing process time by 90%.

  • Project Name: SABR-based Stock Option Volatility Valuation Model Automation
  • Duration: 8 months (July 2022 – February 2023)
  • Focus: Migrating from manual, heuristic-based calibration to fully automated SABR-based valuation
  • Instruments: Stock options (KRW, USD, JPY denominated)

Problem Background

2.1 Limitations of the Existing Mixture Model

The legacy system used an Excel VBA-based Log-Normal Mixture model characterized by:

  • High Parameter Count: 20+ calibration parameters introduced degrees of freedom and computational complexity;
  • Nonlinearity: The optimization landscape was highly nonlinear, frequently converging to local minima;
  • Manual Intervention Required: Traders manually adjusted parameters based on experience, introducing subjectivity and delays;
  • Slow Process: Full calibration and validation took ~5 hours per trading day;
  • Fragile: Small input changes sometimes caused divergence or unrealistic implied volatility surfaces.

2.2 Why SABR?

The SABR model is a stochastic volatility framework with several advantages:

\begin{aligned} d F_t &= \alpha_t F_t^\beta dW_1^F \\ d \alpha_t &= \nu \alpha_t dW_2^\alpha \\ \text{corr}(dW_1^F, dW_2^\alpha) &= \rho \end{aligned}
  • Parsimonious: Only 4 parameters ($\alpha$, $\beta$, $\nu$, $\rho$) vs. 20+ in the mixture model;
  • Theoretically Grounded: Based on stochastic volatility theory rather than ad-hoc curve fitting;
  • Interpretable: Each parameter has clear financial meaning (volatility of volatility, correlation, etc.);
  • Stability: Fewer degrees of freedom and clearer optimization landscape reduce convergence issues;
  • Closed-form Asymptotics: Provides explicit implied volatility formulas suitable for fast computation.

Solution Approach

3.1 Model Transition Strategy

The migration was conducted in phases to ensure stability and allow parallel validation:

  • Phase 1: Implement SABR calibration in Python alongside existing VBA system;
  • Phase 2: Back-test SABR-generated surfaces against historical market data;
  • Phase 3: Convert manual calibration rules to automated parameter selection logic;
  • Phase 4: Integrate with downstream systems (pricing engines, risk modules, reporting).

3.2 Automated Calibration Logic

The key innovation was converting trader experience-based rules into a deterministic algorithm:

  • Initial Parameter Guess: Start with market-implied values from liquid ATM options;
  • Optimization Framework: Use scipy.optimize with L-BFGS-B for constrained nonlinear programming;
  • Objective Function: Minimize weighted sum of squared errors between model and market implied volatilities, with weights emphasizing high-activity strike ranges;
  • Bounds and Constraints: Impose economically meaningful constraints (e.g., $0 < \beta < 1$, $-1 < \rho < 1$);
  • Validation Checks: Automatically reject solutions with unrealistic properties (e.g., negative volatility).

3.3 System Architecture

The automation pipeline comprises:

Component Technology Function
Market Data Ingestion Python + APIs Fetch option prices and market data in real-time
SABR Calibration Engine Python (scipy, numpy) Estimate $(\alpha, \beta, \nu, \rho)$ parameters
Volatility Surface Generation Python (numpy, matplotlib) Create smooth IV surfaces across strikes and maturities
Database Storage MariaDB / Oracle Store computed surfaces for downstream use
Visualization & QA Python + matplotlib Generate charts and validation reports
Notifications Telegram Bot API Alert on completion or errors

3.4 Fallback and Error Handling

  • Optimizer Failure: If SABR calibration fails, system falls back to simpler interpolation;
  • Outlier Detection: Market data anomalies flagged for manual review;
  • Timeout Protection: Calibration aborted if it takes >30 minutes, reusing previous day's parameters;
  • Audit Trail: All decisions logged for post-close review.

Results and Impact

4.1 Process Time Reduction

Step Old System (VBA) New System (Python+SABR) Improvement
Data collection & cleaning 20 min 5 min 75%
Manual parameter adjustment 180 min 0 min (automated) 100%
Calibration computation 120 min 15 min 88%
Validation & output 40 min 10 min 75%
Total Duration ~360 min (6 hours) ~30 min 92% reduction

4.2 Automation Level

The system evolved from semi-automated to fully autonomous:

  • Before: Automated data collection, but manual parameter tuning and validation;
  • After: End-to-end automation; human role reduced to monitoring and exception handling;
  • Frequency: Can now run multiple times per day if needed, enabling intra-day model updates.

4.3 Improved Stability

  • Convergence Rate: Reduced parameter count improved convergence success from 85% to 98%;
  • Reproducibility: Identical inputs now produce identical surfaces (no trader subjectivity);
  • Surface Quality: SABR surfaces exhibit more stable extrapolation behavior away from liquid strikes.

4.4 Infrastructure Efficiency

  • Disk Usage: SABR parameters ($\approx$ 16 bytes) vs. full surface grids ($\approx$ 500 KB); can now store historical surfaces compactly;
  • Computational Resources: Python implementation uses less CPU than VBA (single-threaded, slow);
  • Scalability: Trivial to add new underlyings or expiration dates.
